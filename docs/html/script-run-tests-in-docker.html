مسیر فایل: scripts/run_tests_in_docker.sh

۱. کاراییش به زبان ساده

زیرساخت مشترک تست (Postgres، Kafka، app-api) را بالا می‌آورد، منتظر آمادگی‌شان می‌ماند، سپس تمام سرویس‌های تست تعریف‌شده در Compose با پروفایل test را یکی‌یکی با docker compose run اجرا می‌کند. در پایان یک جدول خلاصه با برچسب‌های PASS / FAIL / SKIPPED چاپ می‌کند و exit code کلی را بر اساس شکست‌های واقعی تنظیم می‌کند — بدون اینکه اولین تستِ شکست‌خورده بقیه را قطع کند.

۲. کجا در پروژه کلی استفاده می‌شود؟

  • راه استاندارد اجرای «همهٔ سوئیت‌های زیرسیستم» روی یک ماشین/CI که Docker دارد، بدون نصب دستی ده‌ها venv.
  • متصل به تعریف سرویس‌های *-tests در docker-compose.yml (پروفایل test).
  • مکمل تست‌های unit محلی هر زیرسیستم: اینجا تمرکز روی اجرای یکنواخت داخل شبکهٔ Compose است.
  • برای developerهایی که می‌خواهند قبل از PR ببینند آیا live/oracle/integrationها هم سبزند.

۳. چیکارا می‌کند؟

  1. وجود .env ریشه و Docker/Compose را چک می‌کند.
  2. سرویس‌های مشترک را up می‌کند و wait می‌زند: Postgres، Kafka، اتمام موفق kafka-init، healthy بودن app-api.
  3. به ترتیب سرویس‌های تست را اجرا می‌کند، از جمله (میان موارد دیگر):
    • app-api-tests
    • crawler-tests و crawler-tests-live (live به Play Store واقعی می‌زند)
    • network-analyzer-tests، -live، -oracle (oracle به tshark نیاز دارد)
    • storage-consumer-tests و -integration
    • sentiment-tests و -integration
  4. خلاصهٔ نتایج را چاپ می‌کند.

برچسب‌های خلاصه:

برچسبمعنا
PASSسوئیت با exit 0 تمام شد.
FAILشکست واقعی تست/اجرا.
SKIPPEDپیش‌نیاز خارجی نیست: اینترنت خروجی فقط برای Play Store داخل crawler-tests-live؛ tshark برای oracle؛ یا image مربوط به sentiment از قبل build نشده — این اسکریپت عمداً sentiment را cold-build نمی‌کند. network-analyzer-tests-live فقط Kafka/App API روی شبکهٔ Compose است و برای «نبود اینترنت» SKIPPED نمی‌شود.

۴. تصمیمات معماری

  • ادامه بعد از شکست: مثل smokeهای ops، می‌خواهیم ببینیم «کدام سوئیت‌ها» شکستند نه فقط اولین‌شان.
  • زیرساخت مشترک یک‌بار: هر سوئیت جداگانه Postgres/Kafka بالا نیاورد؛ زمان و flakiness کمتر می‌شود.
  • تفکیک SKIPPED از FAIL: نبود اینترنت یا image سنگین sentiment نباید کل pipeline را قرمز معنایی کند؛ سیگنال «تست خراب است» باید تمیز بماند.
  • عدم cold-build sentiment: image مدل سنگین است؛ مجبور کردن هر developer به build سرد، هزینهٔ نامتناسب می‌سازد. اگر image نباشد → SKIPPED.
  • --no-build: برای تکرار سریع وقتی imageها از قبل آماده‌اند.
  • پروفایل Compose test: سرویس‌های تست وارد استک production روزمره نمی‌شوند مگر عمداً با این اسکریپت/پروفایل.

۵. دستورات

# از ریشهٔ مخزن؛ نیاز به .env
./scripts/run_tests_in_docker.sh

# بدون rebuild imageها
./scripts/run_tests_in_docker.sh --no-build

./scripts/run_tests_in_docker.sh --help

پیش‌نیاز: فایل .env ریشه؛ Docker Engine + پلاگین Compose. برای liveها: اینترنت خروجی. برای oracle: image با tshark. برای sentiment: image از قبل ساخته‌شده.
