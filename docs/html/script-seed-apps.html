← بازگشت به فهرست اسکریپت‌ها

مسیر فایل: scripts/seed_apps.sh

مستند Application Registry در Application Registry مدل و API را شرح می‌دهد؛ این صفحه روی خودِ اسکریپت seed تمرکز دارد.

۱. کاراییش به زبان ساده

این اسکریپت لیست ثابت و ازپیش‌تعریف‌شدهٔ اپ‌های PlayPulse را از روی host (نه از داخل کانتینر دیگر) به App API ثبت می‌کند: برای هر اپ یک POST /api/applications/ می‌زند. اگر اپ تازه ساخته شود [OK]، اگر از قبل وجود داشته باشد [SKIP] (HTTP 409)، و در غیر این صورت [FAIL]. اجرا idempotent است؛ چندبار صدا زدنش بی‌ضرر است. هدف عملیاتی‌اش این است که قبل از شروع crawler، registry خالی نباشد تا اولین چرخهٔ crawl روی همان لیست seed کار کند — نه روی صفر اپ.

۲. کجا در پروژه کلی استفاده می‌شود؟

  • خودکار داخل bring_up.sh: بعد از سبز شدن healthcheck مربوط به app-api و قبل از بالا آوردن crawler / storage-consumer.
  • دستی: وقتی registry را خالی کرده‌اید، یا می‌خواهید بدون bring_up کامل فقط لیست اولیه را دوباره هم‌تراز کنید.
  • نه داخل run_tests_in_docker.sh برای crawler-tests: آن سوئیت با marker not live و Mock کار می‌کند و به لیست واقعی DB وابسته نیست؛ seed آنجا لازم نیست.
  • همیشه از host به localhost:${APP_API_PORT} وصل می‌شود (پورت publishشدهٔ Compose)، نه به نام سرویس app-api داخل شبکهٔ داکر.

۳. چیکارا می‌کند؟

  1. آدرس پایه را از env می‌سازد: پیش‌فرض APP_API_BASE_URL=http://localhost:${APP_API_PORT:-8000}؛ هر دو متغیر قابل override هستند.
  2. برای هر ردیف از جدول ثابت زیر، JSON با فیلدهای package_name، display_name، category، is_messaging_app، is_active، is_iranian_app می‌سازد و POST می‌کند.
  3. کد وضعیت را گزارش می‌کند (سبک رنگی شبیه check_infra.sh):
    • [OK] — HTTP 201 (ساخته شد)
    • [SKIP] — HTTP 409 (duplicate؛ از قبل ثبت شده)
    • [FAIL] — هر چیز دیگر (یا قطع ارتباط)
  4. اعمال پرچم is_active: لایهٔ create در App API فعلاً is_active را هنگام ساخت نادیده می‌گیرد و اپ همیشه فعال ساخته می‌شود. اسکریپت بعد از 201/409 با POST .../deactivate/ یا .../reactivate/ وضعیت نهایی را با جدول seed هم‌تراز می‌کند (مثلاً MyRightel غیرفعال می‌ماند).
  5. اگر حداقل یک [FAIL] واقعی رخ دهد (نه SKIP)، با exit غیرصفر تمام می‌شود تا bring_up ادامه ندهد.

۴. تصمیمات معماری

  • Seed از host با curl: وابستگی به image جدا یا Django management command ندارد؛ همان API عمومی registry را تمرین می‌کند که crawler هم مصرف می‌کند.
  • Idempotent با 409: روی سرور زنده و volume باقی‌مانده، دوباره آوردن استک اپ‌های قبلی را خراب نمی‌کند.
  • لیست داخل اسکریپت (نه فایل خارجی): منبع حقیقت واحد و قابل‌بازبینی در git؛ مقادیر package name و پرچم‌ها نهایی‌اند و نباید با جستجوی Play Store جایگزین شوند.
  • جبران محدودیت create نسبت به is_active: به‌جای دور زدن API، از endpointهای صریح deactivate/reactivate استفاده می‌شود تا intent کسب‌وکار روشن بماند.
  • شکست جزئی = exit غیرصفر: bring_up نباید crawler را روی registry ناقص راه بیندازد.
  • جدا از پروفایل test: تست‌های واحد crawler mock می‌شوند؛ seed مال استک واقعی / bring_up است.

۵. دستورات

# معمولاً لازم نیست دستی بزنید؛ bring_up خودش صدا می‌زند.
# پیش‌نیاز: app-api سالم و پورت روی localhost publish شده باشد.

./scripts/seed_apps.sh

# override آدرس / پورت
APP_API_PORT=8000 ./scripts/seed_apps.sh
APP_API_BASE_URL=http://localhost:8000 ./scripts/seed_apps.sh

# بررسی نتیجه
curl -sS "http://localhost:${APP_API_PORT:-8000}/api/applications/" | python3 -m json.tool
curl -sS "http://localhost:${APP_API_PORT:-8000}/api/applications/?is_active=true" | python3 -c \
  'import json,sys; print(len(json.load(sys.stdin)), "active apps")'

پیش‌نیاز: curl و python3 روی host؛ سرویس app-api در حال اجرا و healthy؛ پورت APP_API_PORT (پیش‌فرض 8000) از host قابل دسترسی.

خروجی: همه OK/SKIP → exit 0؛ حداقل یک FAIL → exit 1.
